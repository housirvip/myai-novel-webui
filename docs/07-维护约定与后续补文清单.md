# 维护约定与后续补文清单

这份文档用于约束 docs 目录的维护边界，防止文档越写越碎、越写越难同步。

## 1. 维护原则

### 1.1 优先写稳定事实

文档优先记录以下内容：

- 项目定位
- 页面职责
- 主要业务流程
- 目录职责
- 路由结构
- 鉴权边界
- 数据获取模式
- 关键维护入口

这些内容的变动频率相对低，维护成本更可控。

### 1.2 不逐行解释代码

文档的职责是帮助读者建立结构化理解，而不是把源码翻译成文字。

### 1.3 真实路径和术语优先

文档中引用的页面名称、路径、目录、核心术语应尽量和当前仓库保持一致，避免出现文档名词与代码名词不一致的问题。

## 2. 哪些改动后要同步更新文档

### 2.1 如果改了核心页面职责

应优先更新：

- `docs/01-产品与业务流程概览.md`
- `docs/02-页面与功能地图.md`

### 2.2 如果改了项目入口、目录组织或分层方式

应优先更新：

- `docs/03-快速开始-开发者.md`
- `docs/04-前端架构概览.md`

### 2.3 如果改了路由、导航或权限边界

应优先更新：

- `docs/02-页面与功能地图.md`
- `docs/05-路由与权限说明.md`

### 2.4 如果改了 API 访问方式、Query 约定或全局状态逻辑

应优先更新：

- `docs/04-前端架构概览.md`
- `docs/06-数据获取与状态管理.md`

### 2.5 如果 README 的启动方式或文档入口变化

应同步更新：

- `README.md`
- `docs/00-文档导航.md`

## 3. 当前刻意不展开的主题

为了控制维护成本，以下主题当前不做大篇幅展开。

### 3.1 完整 API 字段手册

原因：

- 字段变化会比较频繁。
- 前端类型和后端契约可能继续调整。
- 这类信息更适合由接口定义或更专门的后端文档承担。

### 3.2 逐组件说明文档

原因：

- 当前项目更适合按页面和分层理解。
- 组件层说明很容易碎片化。

### 3.3 截图式操作手册

原因：

- UI 一旦变化，截图立刻过时。
- 当前更需要结构化理解，而不是培训教材形式的说明。

### 3.4 逐页面像素级交互规范

原因：

- 当前项目阶段还不需要把前端行为写成设计规范文档。

### 3.5 完整权限矩阵

原因：

- 当前更适合先说明登录态守卫和页面访问边界。
- 如果未来出现更复杂的角色体系，再补专门权限文档更合理。

## 4. 未来可以按需补充的主题

当项目继续扩展后，可以考虑补以下专题文档：

- workflow 任务与阶段流转专题
- 资源模型专题
- 测试策略与示例专题
- 部署与环境变量专题
- 前后端联调约定专题

前提是这些主题已经足够稳定，并且确实能降低协作成本。

## 5. 当前建议的文档结构边界

这套文档当前更适合承担下面的职责：

- 帮助人快速理解系统
- 帮助新人快速接手项目
- 帮助维护者快速定位代码入口
- 帮助协作者理解页面与流程关系

不适合承担下面的职责：

- 替代源码
- 替代接口规范
- 替代详细测试方案
- 替代设计稿

## 6. 维护时的一个简单检查清单

每次更新文档时，可以快速检查：

1. 文档内容是否仍然对应当前代码结构。
2. 是否和其他文档产生了大段重复。
3. 是否写入了太容易过期的实现细节。
4. 是否真正帮助后续读者节省理解成本。
5. README 与 docs 首页的入口是否仍然一致。

## 7. 建议的长期策略

最稳妥的方式不是不断把文档写得更长，而是保持：

- 首页清晰
- 主题边界明确
- 内容尽量稳定
- 关键变化及时同步

这样这套文档才会真正成为可持续维护的项目资产。
