# 前端架构概览

这份文档从代码组织和职责分层的角度，说明当前前端是如何组织起来的。它的目标不是替代源码，而是帮助维护者更快判断“某一类改动应该落在哪一层”。

## 1. 架构总览

这个项目是一个基于 React 的单页应用，整体结构可以概括为：

- `app` 层负责应用入口、Provider、路由、鉴权和布局壳。
- `pages` 层负责页面级业务编排。
- `components` 层负责可复用的 UI 片段和共享编辑能力。
- `lib` 层负责 API、类型、路径、Query 约定和通用工具。

从依赖方向看，通常是：

- `app` 调用 `pages`
- `pages` 调用 `components` 和 `lib`
- `components` 调用 `lib`
- `lib` 尽量保持在较底层，不依赖页面

## 2. 应用启动链路

应用启动的主链路比较清晰：

1. `src/main.tsx` 负责挂载应用。
2. `src/app/App.tsx` 作为根组件组合 Provider 和 Router。
3. `src/app/providers.tsx` 注入 QueryClientProvider 和 AuthProvider。
4. `src/app/router.tsx` 注册应用全部路由。
5. `src/app/layouts/AppShell.tsx` 作为页面公共外壳渲染导航、顶部信息和页面容器。

这意味着：

- 如果你改的是全局上下文，先看 `providers.tsx`。
- 如果你改的是路由结构，先看 `router.tsx`。
- 如果你改的是全局导航和页面骨架，先看 `AppShell.tsx`。

## 3. `src/app`：应用级能力

`src/app` 是应用级目录，不承载具体业务数据本身，而是为页面运行提供基础设施。

主要职责包括：

- 根组件装配
- Provider 注入
- 路由定义
- 应用整体布局
- 会话状态管理
- 登录态守卫

其中几个关键文件：

- `src/app/App.tsx`：最薄的一层，负责把 Provider 和 Router 组合起来。
- `src/app/providers.tsx`：挂载 QueryClientProvider 和 AuthProvider。
- `src/app/router.tsx`：集中定义登录、注册、书籍、章节、资源、阅读、设置等页面路由。
- `src/app/layouts/AppShell.tsx`：渲染全局侧栏、顶部信息、当前用户和主内容区域。
- `src/app/auth.tsx`：负责读取会话、暴露 `login` / `register` / `logout` / `refresh`。
- `src/app/route-guards.tsx`：对受保护页面和仅游客页面做访问控制。

## 4. `src/pages`：页面级业务编排

`src/pages` 是最接近业务表达的一层。页面通常会同时承担以下责任：

- 发起 query 和 mutation
- 组织页面布局与子区域
- 处理页面内局部状态
- 根据业务上下文决定跳转、提示和交互

当前核心页面包括：

- `src/pages/auth/*`：登录和注册
- `src/pages/books/BooksPage.tsx`：书籍总览
- `src/pages/books/BookDashboardPage.tsx`：书籍工作台
- `src/pages/chapters/ChapterWorkbenchPage.tsx`：章节工作台
- `src/pages/resources/ResourcesPage.tsx`：资源中心
- `src/pages/library/ChapterReaderPage.tsx`：章节阅读
- `src/pages/settings/UserSettingsPage.tsx`：个人设置

这层的一个明显特点是：页面通常直接调用 `src/lib/*-api.ts` 和 `queryKeys`，并用 React Query 管理服务端状态。

## 5. `src/components`：复用 UI 与共享编辑逻辑

`src/components` 目前最值得关注的是资源编辑相关能力。

关键文件包括：

- `src/components/resources/ResourceEditorForm.tsx`
- `src/components/resources/resource-editor-shared.ts`

它们的价值在于：

- 将资源编辑表单的公共逻辑集中起来。
- 支持多种资源类型共用一套编辑能力。
- 被资源中心和章节工作台同时复用。

这说明当前项目虽然没有大规模抽象，但已经在“高复用、高业务密度”的位置做了共享沉淀。

## 6. `src/lib`：共享底层能力与边界封装

`src/lib` 承载了大部分非页面、非展示层的基础能力，是这套前端的稳定底层。

### 6.1 API 封装

- `src/lib/api.ts`

这里统一处理：

- `fetch` 请求
- JSON 响应校验
- 统一错误类型
- 401 未授权错误识别
- 错误提示格式化

### 6.2 领域接口模块

接口不是全部堆在一个文件，而是按领域拆分，例如：

- `auth-api.ts`
- `books-api.ts`
- `chapters-api.ts`
- `resources-api.ts`
- `user-settings-api.ts`
- `workflows-api.ts`

这种组织方式让页面可以按业务领域引用对应接口，而不是直接操作原始 `fetch`。

### 6.3 Query 约定

- `src/lib/query/query-client.ts`
- `src/lib/query/query-keys.ts`

这里集中管理：

- 全局 QueryClient
- 查询默认配置
- 未授权状态的统一处理
- query key 命名空间

### 6.4 路由工具

- `src/lib/routes.ts`

这里统一放：

- 路径生成函数
- 路由参数解析函数

好处是页面不需要到处手写字符串路径。

### 6.5 类型定义

- `src/lib/types.ts`

这里集中定义应用的主要数据模型，包括：

- 用户与会话
- 书籍与章节
- workflow 任务
- 各类资源实体
- 用户运行配置

这使得页面、接口和表单在数据结构上能共享同一套类型来源。

## 7. 当前前端的核心设计取向

从代码现状看，这个项目有几个明确取向：

### 7.1 页面驱动业务

业务逻辑主要落在页面层，由页面负责把 Query、Mutation、局部状态和页面结构组织起来。

### 7.2 服务端状态优先

与其把很多数据复制到本地状态里，这个项目更偏向用 React Query 管理服务端状态，让页面围绕 query key 和失效策略工作。

### 7.3 路由集中管理

路由结构集中在 `src/app/router.tsx`，路径构造集中在 `src/lib/routes.ts`，便于统一维护。

### 7.4 共享逻辑按价值抽取

不是所有东西都过早抽象，但在资源编辑这种跨页面复用明显的场景，已经做了共享能力沉淀。

## 8. 改动应该落在哪一层

### 改页面交互或展示

优先改对应 `src/pages/...` 文件。

### 改全局导航、主布局、登录后页框

优先改 `src/app/layouts/AppShell.tsx`。

### 改登录态恢复、认证上下文、登录/注销流程

优先改：

- `src/app/auth.tsx`
- `src/app/route-guards.tsx`
- `src/lib/auth-api.ts`

### 改 API 访问方式或错误约定

优先改：

- `src/lib/api.ts`
- 对应领域的 `*-api.ts`

### 改 Query 缓存或 key 组织

优先改：

- `src/lib/query/query-client.ts`
- `src/lib/query/query-keys.ts`

### 改资源编辑表单或资源保存逻辑

优先改：

- `src/components/resources/resource-editor-shared.ts`
- `src/components/resources/ResourceEditorForm.tsx`
- 再根据需要回到对应页面

## 9. 当前不需要过度抽象的地方

从目前体量看，这个项目还不需要：

- 把每个页面再拆成复杂的 feature package
- 引入额外的全局状态管理库
- 为所有 UI 片段单独建立设计系统文档

更合适的方向是继续保持当前分层清晰、边界明确、按复用价值抽取共享逻辑的方式。

## 10. 推荐的理解方法

如果你需要向别人解释这套前端，可以用一句话概括：

> 它是一个以页面为主要业务编排单元、以 React Query 管理服务端状态、以 `lib` 作为共享边界层的 AI 小说工作流前端控制台。

这句话基本能够准确描述当前项目的核心架构取向。
