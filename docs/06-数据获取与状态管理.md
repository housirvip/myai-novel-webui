# 数据获取与状态管理

这份文档说明当前前端如何与后端通信、如何组织服务端状态、如何处理鉴权失效，以及类型和 query key 的约定放在哪里。

## 1. 总体思路

当前项目把数据流组织成三层：

1. `src/lib/api.ts`：统一 HTTP 请求与错误处理。
2. `src/lib/*-api.ts`：按业务领域封装具体接口。
3. 页面中的 `useQuery` / `useMutation`：组织数据读取、更新和缓存失效。

服务端状态由 TanStack React Query 管理，而不是把接口结果大面积复制到本地状态中。

## 2. API 请求的统一入口

HTTP 请求封装在：

- `src/lib/api.ts`

这里做了几件关键事情：

- 默认通过 `fetch` 发送请求。
- 默认带上 `credentials: "include"`，说明会话依赖 cookie 或同类凭据。
- 默认声明 `Accept: application/json`。
- 当有请求体时自动附带 `Content-Type: application/json`。
- 统一处理 `204 No Content`。
- 要求响应为 JSON。
- 把错误包装成统一的 `ApiError` 或 `ApiUnauthorizedError`。
- 提供 `formatApiErrorMessage()` 统一格式化错误提示。

这意味着页面层通常不需要自行重复写底层 `fetch` 逻辑。

## 3. 响应约定

从 `src/lib/api.ts` 可以看出，前端当前假设后端遵循以下风格：

### 成功响应

```json
{
  "data": ...
}
```

### 失败响应

```json
{
  "error": {
    "code": "...",
    "message": "...",
    "details": ...
  }
}
```

如果响应不是 JSON，前端会把它视为无效响应并抛错。

## 4. 领域接口如何拆分

具体接口按业务领域拆在 `src/lib/*-api.ts` 中，例如：

- `auth-api.ts`
- `books-api.ts`
- `chapters-api.ts`
- `resources-api.ts`
- `user-settings-api.ts`
- `workflows-api.ts`

这种组织方式的好处是：

- 页面按领域引用接口，更容易理解。
- API 边界更清楚。
- 不同业务模块之间不会把调用逻辑混在一起。

## 5. Query Client 的职责

全局 QueryClient 定义在：

- `src/lib/query/query-client.ts`

它负责：

- 创建全局 QueryClient
- 配置默认查询选项
- 统一处理查询或 mutation 中的 401 未授权错误

当前默认策略包括：

- `staleTime: 10_000`
- `refetchOnWindowFocus: false`
- `retry: 1`

这说明当前前端选择的是较温和的自动刷新策略，避免窗口切回时无条件重新拉取。

## 6. 401 未授权是如何处理的

在 `query-client.ts` 中，如果查询或 mutation 抛出 `ApiUnauthorizedError`，会统一把：

- `queryKeys.authSession()`

更新为 `{ user: null }`。

这会让应用层感知“当前用户已失去登录态”，从而触发页面守卫的后续行为。它的意义是：

- 不需要每个页面都自己判断 401 后怎么清 session。
- 登录态失效具有统一表现。

## 7. Query Key 约定

Query key 集中定义在：

- `src/lib/query/query-keys.ts`

当前 key 设计大体按业务域组织，例如：

- `authSession`
- `userRuntimeSettings`
- `books`
- `book(bookId)`
- `chapters(bookId)`
- `chapter(bookId, chapterNo)`
- `chapterWorkflowState(bookId, chapterNo)`
- `chapterStage(bookId, chapterNo, stage)`
- `chapterStageHistory(bookId, chapterNo, stage, limit)`
- `workflowTask(taskId)`
- `latestChapterWorkflowTask(bookId, chapterNo, workflowType)`
- `chapterWorkflowTasks(bookId, chapterNo, limit)`
- `resourceList(bookId, resourceType, filters)`

这种命名方式的优点是：

- 看到 key 就能大致知道它对应什么领域数据。
- 页面做失效处理时目标更明确。
- 方便统一搜索和维护。

## 8. 会话状态也是服务端状态的一部分

认证上下文定义在：

- `src/app/auth.tsx`

但它并不是自己单独维护一套 session store，而是基于 Query：

- `getSession()` 通过 `useQuery` 拉取
- `login` / `register` / `logout` 通过 `useMutation` 执行
- 成功后通过 `queryClient.setQueryData()` 和 `invalidateQueries()` 更新全局状态

这说明：

- 登录态属于“全局服务端状态 + 应用级上下文封装”的组合。
- AuthProvider 更像是 Query 之上的适配层。

## 9. 页面层如何使用这些数据

页面通常会这样组织数据流：

1. 通过 `queryKeys` 定义 queryKey。
2. 通过领域 `*-api.ts` 提供 queryFn 或 mutationFn。
3. 在 mutation 成功后调用 `invalidateQueries` 或 `setQueryData`。
4. 根据 query 状态渲染 loading / error / success UI。

例如：

- 书籍总览页：拉取书籍列表，创建书籍后失效 `books()`。
- 书籍工作台：同时拉取书籍、章节、资源和用户默认运行配置。
- 章节工作台：同时处理章节、阶段内容、workflow 状态、任务状态和资源数据。
- 个人设置页：读取、更新、清空用户运行配置。

## 10. 类型定义放在哪里

数据结构主要集中在：

- `src/lib/types.ts`

这里统一定义：

- 用户与 session
- 用户运行配置
- 书籍与章节
- workflow 输入输出
- workflow 任务
- 各类资源实体

这份文件对理解业务模型非常重要，因为它基本反映了前端与后端交互的数据面。

## 11. 页面本地状态与服务端状态的边界

当前代码中，本地状态主要用来承载：

- 表单输入
- 当前标签页
- 当前选中项
- 仅影响当前页面显示的开关状态

而这些内容通常不应该放进 Query：

- 输入框当前值
- 当前打开的弹窗
- 当前选择的资源 tab
- 阅读页字号或暗色模式开关

相反，以下内容更适合保持在 Query 中：

- 书籍列表
- 单本书数据
- 章节列表与章节内容
- workflow 状态与任务历史
- 资源列表
- 用户运行配置
- 当前 session

## 12. 新增接口时的建议

如果你要新增一个接口，建议按下面顺序做：

1. 先确认对应的数据结构是否应该补到 `src/lib/types.ts`。
2. 在对应领域的 `*-api.ts` 中新增调用函数。
3. 如果需要缓存，补充或复用 `queryKeys`。
4. 在页面中接入 `useQuery` 或 `useMutation`。
5. 明确 mutation 成功后应该失效哪些 key。

## 13. 维护时需要避免的情况

### 不要在页面里重复手写底层 fetch

否则会绕开统一错误处理和鉴权行为。

### 不要随意发明不一致的 query key

否则缓存失效会变得混乱。

### 不要把服务端状态复制成多份本地状态长期保存

否则很容易出现页面数据和缓存数据不同步。

### 不要把会话问题只修在单页面里

如果是 401 或登录态失效，优先检查全局 Query 与 Auth 的组合逻辑。

## 14. 一句话心智模型

可以把这套数据流理解为：

> `api.ts` 统一底层请求，`*-api.ts` 定义业务接口，React Query 管理缓存和状态，页面负责把这些能力编排成可用的业务界面。

这就是当前前端的数据获取与状态管理主线。
